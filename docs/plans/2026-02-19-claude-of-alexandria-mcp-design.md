# Design: Claude of Alexandria MCP Server

**Date:** 2026-02-19
**Status:** Approved (Revised after second design review)
**Author:** Dawid (davebream)

---

## Problem

The `biblical-segmentation` skill relies on four Python scripts to query 139MB of reference data (Levinsohn discourse features, Masoretic paragraph markers, vocabulary frequencies, morphological parsing). These scripts require Claude Code's Bash tool to execute.

Claude Desktop users cannot run Python scripts. Additionally, the Claude Desktop skill upload has a 30MB uncompressed ZIP limit. This means Desktop users get only the methodology (SKILL.md) with none of the data-driven scholarly analysis that makes the skill valuable.

The ZIP size is a secondary concern. The primary problem is that **Desktop users have no way to access the reference data at all**.

## Solution

Replace the four Python parser scripts with a single TypeScript MCP server: **claude-of-alexandria-mcp**.

The server compiles all reference data (JSON/YAML) into a SQLite database at build time and exposes four query tools over the MCP protocol. Both Claude Code and Claude Desktop can call MCP tools, giving both platforms full functionality.

## Architecture

### MCP Server

Single TypeScript package published to npm as `claude-of-alexandria-mcp`. Lives inside the plugin directory for clean `${CLAUDE_PLUGIN_ROOT}` path resolution.

```
plugins/claude-of-alexandria/servers/claude-of-alexandria-mcp/
├── src/
│   ├── index.ts              # MCP server entry point (stdio transport)
│   ├── tools/
│   │   ├── discourse.ts      # query_discourse_features (replaces levinsohn_parser.py)
│   │   ├── paragraphs.ts     # query_paragraph_breaks (replaces sefaria_paragraphs.py)
│   │   ├── vocabulary.ts     # query_vocabulary (replaces vocabulary_parser.py)
│   │   └── morphology.ts     # query_morphology (replaces morphology_parser.py)
│   └── db/
│       ├── query.ts          # SQLite query layer (sql.js, parameterized statements)
│       └── books.ts          # Book name normalization lookup
├── scripts/
│   └── build-db.ts           # ETL: Convert JSON/YAML source data → SQLite
├── data/
│   └── biblical.sqlite       # Build artifact, shipped with package
├── package.json
└── tsconfig.json
```

### SQLite Driver: sql.js (WASM)

Use `sql.js` (pure WebAssembly SQLite) instead of `better-sqlite3` (native C++ addon). Rationale:

- **No C++ toolchain required** — Desktop users running `npx` don't need build tools
- **Cross-platform by default** — works on macOS, Linux, Windows without platform-specific binaries
- **No prebuild/postinstall scripts** — simpler npm package, fewer failure modes
- **Trade-off**: ~2x slower than native `better-sqlite3`, but queries against a ~40MB database are sub-second regardless

**Memory considerations:** sql.js loads the entire database into WASM linear memory. For a ~40MB database, expect 80-150MB process RSS (database bytes + WASM heap overhead + internal structures). This is acceptable for a single-user local MCP server running alongside Claude.

**Lazy loading:** The database is loaded on first tool invocation, not at server startup. This keeps MCP server registration instant and avoids memory allocation until actually needed.

**All queries use parameterized statements** (`db.exec("SELECT ... WHERE book = ?", [book])`) to prevent bugs with special characters in Greek/Hebrew text.

### Data Pipeline

```
reference/levinsohn/*.json           ─┐
reference/masoretic/*.json           ─┤
reference/vocabulary/nt_lemmas.yaml  ─┤
reference/vocabulary/ot_lemmas.yaml  ─┼── build-db.ts ──→ biblical.sqlite
reference/vocabulary/nt_clusters.yaml─┤
reference/vocabulary/semantic_groups.yaml─┤
reference/morphology/**/*.json       ─┘
```

Specific source files per table:
- `discourse_features` — all `reference/levinsohn/*.json` files (each file contains references across all NT books)
- `paragraph_markers` — all `reference/masoretic/*.json` files
- `vocabulary` — `nt_lemmas.yaml` and `ot_lemmas.yaml` (chapter-level aggregated data, not per-book JSON files)
- `vocabulary_clusters` — `nt_clusters.yaml` (NT only; OT clusters not yet available)
- `thematic_keywords` — `semantic_groups.yaml` + hardcoded constants from `vocabulary_parser.py`
- `morphology` — all `reference/morphology/**/*.json` files

The raw JSON/YAML files remain in the repository as source-of-truth. The SQLite database is a build artifact generated by `build-db.ts`. The per-book JSON files in `reference/vocabulary/nt/*.json` and `reference/vocabulary/ot/*.json` are verse-level data not used by `build-db.ts` — the chapter-level YAML aggregations are the correct source for the `vocabulary` table.

### Book Name Normalization

All tools accept book names in any common form and normalize internally. The server maintains a lookup table mapping variants to a canonical form.

**Canonical form:** lowercase with underscores (e.g., `1_corinthians`, `song_of_songs`).

| Input variants | Canonical form |
|---|---|
| "1 Cor", "1Cor", "I Corinthians", "1 Corinthians" | `1_corinthians` |
| "Gen", "Genesis" | `genesis` |
| "Ps", "Psalm", "Psalms" | `psalms` |

Note: Source data uses different conventions — masoretic files use hyphens (`2-chronicles.json`), morphology uses underscores (`1_corinthians.json`), vocabulary YAML uses title case (`Matthew`), `bible_utils.py` uses hyphens (`1-samuel`). The `build-db.ts` ETL normalizes all these into the canonical lowercase underscore form.

Normalization rules:
1. Case-insensitive matching
2. Strip leading/trailing whitespace
3. Expand common abbreviations (standard SBL abbreviations)
4. Store canonical form in SQLite; normalize at query time before WHERE clauses
5. Return the human-readable form (e.g., "1 Corinthians") in output

The full mapping table is built into `src/db/books.ts` as a static lookup — not in SQLite, since it's configuration, not data. Each book entry also carries a `testament` field (`nt` or `ot`) used for testament-scoping validation.

### SQLite Schema

```sql
-- Levinsohn NT discourse features (from reference/levinsohn/*.json)
-- Note: Levinsohn files store refs as "Matt 2:13" strings; ETL parses these
-- using the book normalization module into separate book/chapter/verse columns.
-- Each file contains references across ALL NT books, not one file per book.
CREATE TABLE discourse_features (
  id INTEGER PRIMARY KEY,
  book TEXT NOT NULL,             -- canonical form: 'mark', 'genesis', etc.
  chapter INTEGER NOT NULL,
  verse INTEGER NOT NULL,
  feature TEXT NOT NULL,          -- 'historical_present', 'left_dislocation', etc.
  feature_description TEXT,       -- file-level description (one per feature, not per reference)
  word TEXT                        -- Greek word form
);
CREATE INDEX idx_discourse_book ON discourse_features(book, chapter, verse);
CREATE INDEX idx_discourse_feature ON discourse_features(feature);

-- Masoretic paragraph markers (from reference/masoretic/*.json)
CREATE TABLE paragraph_markers (
  id INTEGER PRIMARY KEY,
  book TEXT NOT NULL,
  chapter INTEGER NOT NULL,
  verse INTEGER NOT NULL,
  marker_type TEXT NOT NULL        -- 'petuchah' or 'setumah'
);
CREATE INDEX idx_markers_book ON paragraph_markers(book, chapter, verse);

-- Vocabulary frequencies (from nt_lemmas.yaml + ot_lemmas.yaml)
-- NT lemmas are Greek text (e.g., "χαίρω")
-- OT lemmas are Strong's numbers (e.g., "H1285") — display text handled at tool level
CREATE TABLE vocabulary (
  id INTEGER PRIMARY KEY,
  book TEXT NOT NULL,
  testament TEXT NOT NULL,         -- 'nt' or 'ot'
  chapter INTEGER NOT NULL,
  lemma TEXT NOT NULL,             -- Greek text (NT) or Strong's number (OT)
  frequency INTEGER NOT NULL
);
CREATE INDEX idx_vocab_book_lemma ON vocabulary(book, lemma);
CREATE INDEX idx_vocab_book_chapter ON vocabulary(book, chapter);
CREATE INDEX idx_vocab_frequency ON vocabulary(book, frequency);

-- Vocabulary clustering (from nt_clusters.yaml; OT clusters not yet available)
-- cluster_chapters array from source YAML is intentionally not preserved;
-- chapter_start/chapter_end captures the range boundaries, which is sufficient
-- for the tool's clustering output format.
CREATE TABLE vocabulary_clusters (
  id INTEGER PRIMARY KEY,
  book TEXT NOT NULL,
  testament TEXT NOT NULL,
  lemma TEXT NOT NULL,
  concentration REAL NOT NULL,     -- 0.0-1.0 (e.g., 0.67 = 67% in range)
  chapter_start INTEGER NOT NULL,  -- parsed from cluster_range string (e.g., "1-22" → 1)
  chapter_end INTEGER NOT NULL,    -- parsed from cluster_range string (e.g., "1-22" → 22)
  total_occurrences INTEGER NOT NULL
);
CREATE INDEX idx_clusters_book ON vocabulary_clusters(book, lemma);

-- Thematic keyword mappings (from semantic_groups.yaml + vocabulary_parser.py constants)
CREATE TABLE thematic_keywords (
  theme TEXT NOT NULL,
  lemma TEXT NOT NULL,             -- Greek text (NT) or Strong's number (OT)
  testament TEXT NOT NULL
);
CREATE INDEX idx_theme ON thematic_keywords(theme, testament);

-- Morphological parsing (from reference/morphology/**/*.json)
CREATE TABLE morphology (
  id INTEGER PRIMARY KEY,
  book TEXT NOT NULL,
  testament TEXT NOT NULL,
  chapter INTEGER NOT NULL,
  verse INTEGER NOT NULL,
  word_position INTEGER NOT NULL,  -- 1-indexed, derived from array position in source JSON
  text TEXT NOT NULL,
  normalized TEXT,                 -- normalized word form (from source JSON 'normalized' field)
  lemma TEXT NOT NULL,
  pos TEXT NOT NULL,                -- 'noun', 'verb', etc.
  parsing TEXT                     -- JSON string: case, number, gender, tense, etc.
);
CREATE INDEX idx_morph_range ON morphology(book, chapter, verse);
CREATE INDEX idx_morph_lemma ON morphology(lemma);
```

### Database Size Validation

The 40MB estimate is unvalidated. The morphology source is 122MB of JSON; even with SQLite compression, the morphology table alone could be 45-90MB. **Phase 1, step 1 gates on this:**

1. Build the database against actual reference data
2. Measure the `.sqlite` file size
3. Measure Node.js process RSS with sql.js loading the database

**If database exceeds 60MB or RSS exceeds 200MB**, consider:
- **Option A:** Split morphology into a separate database file, loaded on demand only when `query_morphology` is called
- **Option B:** Encode the `parsing` column as a compact string (e.g., `V-AMP-NSM`) instead of JSON, expanding at query time (60-80% column size reduction)
- **Option C:** Both

This validation is a hard gate — do not proceed with tool implementation until the single-file architecture is confirmed viable.

### Clustering Computation

The `build-db.ts` script precomputes vocabulary clusters during the ETL phase, matching the logic from `analyze_clusters.py` (not `vocabulary_parser.py`, which only reads precomputed `nt_clusters.yaml`).

Algorithm (from `analyze_clusters.py`):
1. For each `(book, lemma)` pair, count occurrences per chapter
2. Skip lemmas with fewer than 5 total occurrences (`MIN_OCCURRENCES = 5`)
3. Slide a window of 2-4 chapters (`MIN_CHAPTERS = 2`, `MAX_CHAPTERS = 4`) to find the densest range
4. Concentration = `occurrences_in_window / total_occurrences`
5. If concentration >= `CLUSTERING_THRESHOLD` (0.6), write to `vocabulary_clusters`
6. The runtime `query_vocabulary` tool reads precomputed clusters — no runtime computation needed

**OT clusters:** Only `nt_clusters.yaml` exists currently. `build-db.ts` computes OT clusters from `ot_lemmas.yaml` using the same algorithm during ETL. If this proves too slow (validate build time stays under 60 seconds), fall back to NT-only clusters and return `{ "has_clustering": false, "clusters": [] }` for OT books.

### Lemma & Theme Metadata

Thematic keyword mappings come from two sources:
1. **`semantic_groups.yaml`** — primary source, contains all themes
2. **Hardcoded constants** in `vocabulary_parser.py` — merged for completeness

Both are compiled into the `thematic_keywords` table by `build-db.ts`.

**No hardcoded theme enum.** The `theme` parameter accepts any string. The tool queries the `thematic_keywords` table; if no rows match, it returns `INVALID_THEME` with the list of available themes. This prevents schema/data drift as `semantic_groups.yaml` evolves.

Available themes (from current `semantic_groups.yaml`): joy, faith, love, righteousness, covenant, glory, salvation, holiness, spirit, wisdom, peace, grace, truth.

### Small YAML References

The following small YAML files remain **outside** MCP server scope — they are read directly by SKILL.md instructions and do not need database storage:

- `book-genres.yaml` — genre classification per book
- `book-exceptions.yaml` — special handling rules
- `genre-methodology.yaml` — genre-specific methodology
- `compositional-debates.yaml` — scholarly debate notes

These are small (24KB total) and are referenced as contextual guidance, not queried data.

## Tool Interfaces

### Error Response Format

All tools return errors in a consistent structure:

```json
{
  "error": {
    "code": "BOOK_NOT_FOUND",
    "message": "Book 'Markk' not found. Did you mean 'Mark'?",
    "suggestions": ["Mark"]
  }
}
```

Error codes:
- `BOOK_NOT_FOUND` — unrecognized book name (includes fuzzy suggestions)
- `INVALID_RANGE` — malformed chapter or verse range (syntactic errors only; out-of-bounds ranges return whatever data exists)
- `NO_DATA` — valid query but no matching records
- `INVALID_TESTAMENT` — testament value not "nt" or "ot"
- `INVALID_THEME` — theme not found in `thematic_keywords` table (includes list of available themes)
- `TESTAMENT_MISMATCH` — querying NT-only tool with OT book or vice versa (e.g., discourse features for Genesis)
- `DB_ERROR` — database file not found, corrupt, or unreadable
- `INTERNAL_ERROR` — unexpected server error

### chapter_range Format

All tools accepting `chapter_range` use the same format:
- `"3"` — single chapter
- `"3-7"` — inclusive range (chapters 3 through 7)
- Omitted — all chapters in the book

Syntactically invalid ranges (e.g., `"7-3"`, `"0-5"`, `"abc"`) return `INVALID_RANGE` error. Out-of-bounds ranges (e.g., `"1-99"` for a 4-chapter book) are valid — the tool returns whatever data exists within the range.

### query_discourse_features

Replaces `levinsohn_parser.py`. **NT books only** — querying an OT book returns `TESTAMENT_MISMATCH`.

**Input:**
```json
{
  "book": "Mark",
  "features": ["historical_present", "left_dislocation"],
  "chapter_range": "1-5"
}
```

- `book` (required): NT book name (any common form, normalized internally)
- `features` (optional): filter to specific features; default: the 6 segmentation-relevant features (`historical_present`, `left_dislocation`, `referential_pod`, `situational_pod`, `reported_speech`, `tail_head_linkage`)
- `chapter_range` (optional): chapter filter

**Output:**
```json
{
  "book": "Mark",
  "chapter_range": "1-5",
  "features": {
    "historical_present": [
      { "chapter": 1, "verse": 12, "word": "ἐκβάλλει", "feature_description": "Highlights not the speech or act..." }
    ]
  },
  "summary": { "historical_present": 42, "left_dislocation": 7 },
  "available_features": ["historical_present", "left_dislocation", "asyndeton", "redundant_quotative_frame"]
}
```

The `available_features` field lists all features present in the data for the queried book, enabling feature discovery without a separate metadata call. The `feature_description` is the file-level description for the feature (one per feature type, not per reference).

### query_paragraph_breaks

Replaces `sefaria_paragraphs.py`. **OT books only** — querying an NT book returns `TESTAMENT_MISMATCH`.

**Input:**
```json
{
  "book": "Genesis",
  "chapter_range": "37-50"
}
```

- `book` (required): OT book name
- `chapter_range` (optional): chapter filter

**Output:**
```json
{
  "book": "Genesis",
  "chapter_range": "37-50",
  "markers": [
    { "chapter": 37, "verse": 2, "type": "petuchah" },
    { "chapter": 37, "verse": 5, "type": "setumah" }
  ],
  "summary": { "petuchot": 12, "setumot": 18, "total": 30 }
}
```

### query_vocabulary

Replaces `vocabulary_parser.py`.

**Input:**
```json
{
  "book": "Philippians",
  "testament": "nt",
  "theme": "joy",
  "check_clustering": true,
  "min_frequency": 3,
  "limit": 200
}
```

- `book` (required): book name
- `testament` (optional): `"nt"` or `"ot"`, default `"nt"`
- `theme` (optional): any theme present in `thematic_keywords` table; returns `INVALID_THEME` with available themes list if not found
- `check_clustering` (optional): include precomputed vocabulary clusters
- `min_frequency` (optional): only return lemmas with frequency >= this value; default 1
- `limit` (optional): maximum number of lemmas to return (sorted by frequency descending); default 200

**Output (with theme):**
```json
{
  "book": "Philippians",
  "testament": "nt",
  "theme": "joy",
  "thematic_matches": [
    { "lemma": "χαίρω", "total": 9, "by_chapter": { "1": 3, "2": 2, "3": 1, "4": 3 } },
    { "lemma": "χαρά", "total": 5, "by_chapter": { "1": 2, "2": 1, "4": 2 } }
  ],
  "clustering": {
    "has_clustering": true,
    "notable_count": 2,
    "clusters": [
      { "lemma": "χαίρω", "concentration": 0.67, "chapter_range": "1-2", "total_occurrences": 9 }
    ]
  }
}
```

**Output (without theme — all lemmas):**
```json
{
  "book": "Philippians",
  "testament": "nt",
  "lemmas": [
    { "lemma": "χαίρω", "total": 9, "by_chapter": { "1": 3, "2": 2, "3": 1, "4": 3 } },
    { "lemma": "πίστις", "total": 7, "by_chapter": { "1": 4, "2": 1, "3": 2 } }
  ],
  "total_lemmas": 247,
  "returned": 200,
  "clustering": null
}
```

When no `theme` is provided, the tool returns lemmas sorted by frequency descending, limited by `limit` parameter. The `clustering` field is only populated when `check_clustering: true`. For OT books, clustering returns `{ "has_clustering": false, "clusters": [] }` until OT cluster data is available.

### query_morphology

Replaces `morphology_parser.py`. Note: this tool serves multiple skills (`biblical-segmentation` and `exegetical-notes`).

**Input:**
```json
{
  "book": "Philippians",
  "range": "1:1-1:11",
  "testament": "nt",
  "pos_filter": "verb",
  "word_filter": "ἐναρξάμενος"
}
```

- `book` (required): book name
- `range` (required): verse range `"chapter:verse-chapter:verse"` or single `"chapter:verse"`
- `testament` (optional): `"nt"` or `"ot"`, default `"nt"`
- `pos_filter` (optional): filter by part of speech
- `word_filter` (optional): filter by word form — matches against `text`, `normalized`, and `lemma` fields (matching Python `morphology_parser.py` behavior)

**Output:**
```json
{
  "book": "Philippians",
  "range": "1:1-1:11",
  "testament": "nt",
  "words": [
    {
      "verse": "1:6",
      "position": 3,
      "text": "ἐναρξάμενος",
      "normalized": "ἐναρξάμενος",
      "lemma": "ἐνάρχομαι",
      "pos": "verb",
      "parsing": { "tense": "aorist", "voice": "middle", "mood": "participle", "case": "nominative", "number": "singular", "gender": "masculine" }
    }
  ],
  "summary": { "total_words": 1, "by_pos": { "verb": 1 } }
}
```

Note: `pos_filter` and `word_filter` are the only supported runtime filters. The `parsing` JSON is returned as-is for display — filtering by individual morphological attributes (e.g., "all aorist participles") is not supported at the query level due to WASM JSON extraction overhead. Callers can filter the returned `parsing` objects in post-processing.

## Plugin Integration

### .mcp.json (at plugin root)

```json
{
  "mcpServers": {
    "claude-of-alexandria-mcp": {
      "command": "node",
      "args": ["${CLAUDE_PLUGIN_ROOT}/servers/claude-of-alexandria-mcp/dist/index.js"],
      "env": {
        "DATA_DIR": "${CLAUDE_PLUGIN_ROOT}/servers/claude-of-alexandria-mcp/data"
      }
    }
  }
}
```

The server lives inside the plugin directory at `plugins/claude-of-alexandria/servers/claude-of-alexandria-mcp/`. When the plugin is installed in Claude Code, `${CLAUDE_PLUGIN_ROOT}` resolves to the plugin directory and the MCP server starts automatically. No user configuration needed.

### Claude Desktop Configuration

Desktop users add to their MCP settings:

```json
{
  "mcpServers": {
    "claude-of-alexandria-mcp": {
      "command": "npx",
      "args": ["-y", "claude-of-alexandria-mcp"]
    }
  }
}
```

One line. npm downloads the published package (containing `dist/` and `data/biblical.sqlite`), caches it, and runs it. First run downloads ~40-60MB of biblical reference data; subsequent runs use the cached package. The repo structure is irrelevant to Desktop users — they get a self-contained npm package.

### Build Pipeline

```bash
# In plugins/claude-of-alexandria/servers/claude-of-alexandria-mcp/
npm run build:db        # ETL: JSON/YAML → SQLite (reads from ../../skills/biblical-segmentation/reference/)
npm run build           # TypeScript → JavaScript
npm run prepublishOnly  # build:db + build (runs before npm publish)
```

Note: Uses `prepublishOnly` (not `prepublish`) to avoid running on `npm install` — only triggers on `npm publish`.

## Migration Plan

### Phase 1: Build MCP Server
1. Initialize TypeScript project in `plugins/claude-of-alexandria/servers/claude-of-alexandria-mcp/`
2. Implement `build-db.ts` — read all reference JSON/YAML, write SQLite (including precomputed clusters)
3. **Hard gate: validate database size.** Build against actual data. Measure `.sqlite` file size and Node.js RSS with sql.js. If >60MB file or >200MB RSS, implement splitting (Option A) or compression (Option B) before proceeding.
4. Implement book name normalization (`src/db/books.ts`)

## Risks

| Risk | Mitigation |
|------|------------|
| Database size exceeds single-file budget | Hard gate in Phase 1 step 3; split morphology or compress parsing column if needed |
| sql.js WASM memory (80-150MB RSS for 40MB DB) | Lazy loading; validate during Phase 1; 200MB ceiling |
| Output parity with Python scripts | Parity testing in Phase 1 step 6; Python scripts preserved as validation baseline |
| sql.js WASM query performance | ~2x slower than native, but sub-second on indexed queries; acceptable |
| Desktop users don't know to install MCP server | README instructions + first-run download size note + skill output notes when tools unavailable |
| Book name variants cause query misses | Normalization layer with fuzzy matching and suggestions in error response |
| Theme enum drift from semantic_groups.yaml | No enum — dynamic lookup against thematic_keywords table |
